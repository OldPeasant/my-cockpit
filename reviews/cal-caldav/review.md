## P3 Low

- [ ] **CR-2 | An out-of-range DURATION or alarm TRIGGER throws ArithmeticException, which no catch handles: one bad resource blocks the whole calendar's sync**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/calendar/infra/caldav/CalDavEventMapping.kt:297` (also `:77-88`, `CalDavCalendarAdapter.kt:299-305`, `:491-495`)
    - Category: Correctness
    - Problem: `duration()` calls `Duration.ofDays(...)`/`plusHours(...)` on any parsed digits. A value like `P200000000000000D` (in DURATION or a VALARM TRIGGER) overflows and throws `ArithmeticException`. `readOrNull` catches only `IllegalArgumentException`/`DateTimeException`, `changes()` catches only `IllegalArgumentException`, and `answer()` rethrows anything else. So the exception escapes `fetchEvents`. The cursor is not advanced, and every following run of that calendar fails with "Unexpected error". On a write, the client gets 500 instead of 502.
    - Why it matters: Arbitrary iCalendar data can reach a CalDAV calendar through shared calendars or invitations. One such resource stops all syncing of the calendar until someone edits it on the server. This contradicts the intent of skipping unreadable VEVENTs.
    - Suggested fix: Return null from `duration()` on overflow (catch `ArithmeticException` there), or add `ArithmeticException` to the catches in `readOrNull`/`answer`.

- [ ] **CR-3 | The CalDavClient documentation says 403 answers throw, but they do not; a 403 during discovery is reported as "No CalDAV service found"**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/calendar/infra/caldav/CalDavClient.kt:23` (behavior at `:114-117`; `CalDavCalendarAdapter.kt:111-121`, `:63-66`)
    - Category: Quality
    - Problem: The class comment says "401/403/5xx answers that the adapter does not handle become CalendarProviderExceptions". `send` throws only for 401 and >= 500. During discovery, `propfind` maps any non-207, including 403, to null, and the user sees "No CalDAV service found at the source's URL".
    - Why it matters: The documentation is misleading, and a permissions problem gets the wrong error message.
    - Suggested fix: Either throw a "no permission" `CalendarProviderException` for 403 in `send` (and keep the 403 handling callers need), or correct the comment and have discovery report non-207 statuses other than 404/405 with their HTTP status.
