## P2 Medium

- [ ] **CR-1 | Valid real-world URLs are rejected with 400 (IDN hosts, underscores, unencoded characters)**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/bookmarks/domain/BookmarkService.kt:255`
    - Category: Correctness
    - Problem: `normalizeUrl` accepts a URL only if `java.net.URI(trimmed)` parses and yields a non-empty `host`. `java.net.URI` is strict RFC 2396: checked with jshell, `https://bücher.de/x` and `https://a_b.example.com/` give `host == null`, and `https://example.org/a b` and `https://example.org/?q=a|b` throw `URISyntaxException`. Each of these is answered with 400 "must be a valid http or https URL". `PageFetcher.target` uses the same strict parser.
    - Why it matters: SPEC.md §8.4 is about saving URLs that users copy from browsers or share from Android apps. Browsers often copy IDN hosts in Unicode form, and many sites put unencoded `|`, spaces or brackets in query strings. Those bookmarks cannot be saved at all.
    - Suggested fix: Make the URL safe before validating it. Convert the host with `java.net.IDN.toASCII`, and percent-encode characters that are not allowed in a URI, for example by parsing with `java.net.URL` and rebuilding with the multi-argument `URI` constructor. Store that form and fetch from it, so the worker's `url ==` comparison still matches. Add 201 cases for an IDN host and a query with `|` to the validation test.

- [ ] **CR-2 | `metadataStatus` can stay `PENDING` forever, and nothing recovers it**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/bookmarks/infra/BookmarkMetadataWorker.kt:416` (also `:445`, `BookmarkService.kt:167`)
    - Category: Correctness
    - Problem: The fetch request only lives in an in-memory `ThreadPoolExecutor`. These cases all leave the row `PENDING` with no worker ever finishing it:
      - the queue is full (only a WARN log);
      - the application stops or restarts (`destroy()` calls `shutdownNow()`, which drops queued tasks; running fetches are interrupted, and in that case the result is still written as `FAILED`);
      - a bookmark is deleted while its fetch runs and is restored later (`applyMetadata` skips trashed bookmarks and nothing re-requests the fetch).

      Nothing at startup or on a schedule looks for stale `PENDING` rows. The API contract (`BookmarkResponse.metadataStatus`, openapi.yaml) tells clients that PENDING means the fetch is running and that a change event follows.
    - Why it matters: Clients that show a "fetching..." state, or wait for the SSE update, wait forever after any deploy or restart that happens while fetches are queued. Only a manual `refresh-metadata` gets the bookmark out of this state. This is the "every path ends loading" class of defect.
    - Suggested fix: On `ApplicationReadyEvent`, re-queue active bookmarks that are still `PENDING`, or periodically re-queue those whose `updatedAt` is older than the fetch timeout. When a request is rejected, store `FAILED` instead of leaving `PENDING`. Have `BookmarkTrashContributor.restore` request a fetch for a `PENDING` bookmark. Add a test for at least the rejected/restart path.

## P3 Low

- [ ] **CR-3 | An older fetch that finishes later can overwrite `metadataStatus` from a newer request for the same URL**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/bookmarks/domain/BookmarkService.kt:167`
    - Category: Correctness
    - Problem: `applyMetadata` only drops results whose URL no longer matches. Suppose an automatic fetch after create (overwrite=false, slow server) and a user `refresh-metadata` (overwrite=true) run for the same URL. If the refresh finishes first and the older fetch fails afterwards, the bookmark ends up `FAILED` even though fresh metadata was stored. If the older one finishes first, `FETCHED` is shown while the refresh is still running.
    - Why it matters: The status shown to clients can be wrong. This is rare (it needs two fetches of one URL in flight at once) and the stored fields stay correct.
    - Suggested fix: Give each request an identity, for example a fetch generation or token stored on the row and carried in `BookmarkMetadataRequested`, and ignore results from superseded requests, as is already done for a URL change.

- [ ] **CR-4 | Mutable test seam `fetcher` is unused and not thread-safe**
    - File: `server/src/main/kotlin/ch/sonensei/cockpit/bookmarks/infra/BookmarkMetadataWorker.kt:401`
    - Category: Quality
    - Problem: `internal var fetcher` is documented as "replaceable in tests", but no test replaces it (grep of `server/src/test`). It is a plain non-volatile field written on one thread and read on the `bookmark-fetch` threads.
    - Why it matters: It is dead mutability that suggests a test hook that does not exist, and swapping it at runtime would be a data race.
    - Suggested fix: Make it a `private val`, or inject a `PageFetcher` bean if a test really needs to replace it.
