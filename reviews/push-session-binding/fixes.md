## Fixed findings

### CR-1 / TW-1 — A subscribe that races with the end of its session answers 500 and logs an ERROR

Files changed:
- `server/src/main/kotlin/ch/sonensei/cockpit/core/push/domain/PushService.kt`
- `server/src/main/kotlin/ch/sonensei/cockpit/core/push/api/PushController.kt`
- `server/src/test/kotlin/ch/sonensei/cockpit/core/push/PushWebTests.kt`

Problem:
`PushService.subscribe` upserts with the session id of the principal resolved at the start of the request. When the
`auth_session` row is deleted in between (logout in another tab, TOTP re-enrollment, `deleteExpired` of another
login), the foreign key `push_subscription.session_id` fails; the `DataIntegrityViolationException` reached
`ProblemDetailsAdvice.handleUnexpected`, which logged an ERROR and answered 500.

Fix:
- `subscribe` wraps the upsert in a `try`; a `DataIntegrityViolationException` whose cause chain has a
  `java.sql.SQLException` with SQLSTATE `23503` (foreign_key_violation) is translated into
  `ErrorResponseException(401, ProblemDetail "The login session has ended")`, logged at DEBUG only (session id, no
  token). Other integrity violations are rethrown unchanged. No further query runs after the failed statement; the
  exception propagates out of the `@Transactional` method, so the (aborted) transaction is rolled back and nothing is
  stored. This mirrors how `PushController` already answers the 403 and how other services (e.g.
  `InvitationService`) throw `ErrorResponseException`, so the shared `core/web` module is unchanged.
- KDoc of `subscribe` documents the 401.
- `PushController` PUT `/api/v1/push/subscriptions`: added an `@ApiResponse` 401 ("Not logged in (no body), or the
  login session ended during the request (Problem Details)"). `api/openapi.yaml` must be regenerated by the parent.
- New test `subscribing with a session that ended during the request gets 401 and stores nothing` in `PushWebTests`:
  creates a principal via `PushTestSessions`, deletes its session, PUT gives 401 `application/problem+json` with
  `status` 401 and no row; then, with an existing subscription of the live owner session, a PUT of the same endpoint
  by the ended session (update path of the upsert) also gives 401 and the stored row keeps its session and keys.

Validation:
- Not run by the fixer: Gradle is not available to sub-agents. The parent must run
  `cd server && ./gradlew test --tests 'ch.sonensei.cockpit.core.push.*'`, `./gradlew ktlintCheck` and regenerate
  `api/openapi.yaml`.

Residual note for the parent:
The application's own ERROR log ("Unhandled exception in REST request") is gone. Hibernate's `SqlExceptionHelper` may
still log the failed SQL statement itself (WARN for the SQLSTATE and, depending on the Hibernate version, ERROR for
the driver message) before the exception is translated; this is the same behaviour as the existing
`DataIntegrityViolationException` catch sites in the codebase (`SetupService`, `LinkService`, `VapidKeyService`, ...).
Please check the test log of the new test; avoiding that log line entirely would need a different upsert design
(e.g. an insert guarded by a locked session lookup) and was judged out of proportion for a P3.
